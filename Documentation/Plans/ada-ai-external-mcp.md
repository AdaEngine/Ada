# Local MCP in Ada AI implementation plan

Date **2026-11-23**. The user approved the [feature design](../Designs/ada-ai-external-mcp.md) in the project conversation and requested Blender first. The local approval record attests to that message.

## First delivery

In a disposable Basic 3D project, ask built-in desktop Ada AI in Build mode to make a small orange traffic cone with a dark base in Blender, place it in view and check it in Play. The first engineering slice uses the real Blender stdio executable on Windows. It carries the asset through the production importer, scene editing and game capture paths. An injected Cloud transport in tests can exercise the production tool loop while the Cloud deployment is being prepared. Release acceptance uses a compatible live Ada Cloud deployment and a complete Studio distribution on both Windows and macOS.

The Windows planning probe started the installed `mcp-for-blender` 2.2.4 server, initialized it and listed nine tools via stdio. It negotiated MCP `2025-11-25` and reported Blender 5.3.0 with add-on 1.8. The `execute_blender_code` tool requires `code` and accepts an optional `user_prompt`. Treat these as the starting compatibility baseline. Record the exact versions and outcomes on both desktop hosts before assigning a supported version range. The probe covered discovery. Export, import, model placement and Play are acceptance checks below.

## 1. Connect and export in Blender

- Add a desktop-owned subprocess service under [`Editor/Sources/AdaEditor/Agent`](../../Editor/Sources/AdaEditor/Agent). Use a resolved executable, ordered arguments, a Studio-owned non-project working directory and a minimal platform environment. Stream stdout and stderr independently. Bound message and queue sizes before decoding, redact local diagnostics, and stop the owned process and pending waits on timeout, cancellation, exit or disconnect. Paths and arguments with spaces must work on both systems.
- Implement newline-delimited JSON-RPC as a separate transport. The AdaMCP `StdioTransport` in the pin currently uses `Content-Length`, while Studio's [`EditorAgentMCPConnection`](../../Editor/Sources/AdaEditor/Agent/EditorAgentMCPConnection.swift) already handles newline buffering in its ACP bridge. Reuse appropriate pipe helpers. Extend AdaMCP `Client` where needed for `initialize` followed by `notifications/initialized`, pagination, tool-list changes, cancellation, structured results and cleanup on EOF. Keep the existing ACP bridge and wire format compatible. If a dependency update is required, validate the adjacent AdaMCP change, update the editor pin and corresponding CI pins together, and test against that exact revision. [MCP stdio specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) · [MCP lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)
- Add the `create_and_export_glb` preset action on the same connector. An approved recipe describes a model name and bounded primitive geometry, transforms and material colors. Use a Studio-owned Blender script and encode the recipe as data. Derive the destination inside a Studio-owned job directory under project-local `Downloads`. Check the negotiated tool identity and schema at the point of dispatch. Send only the inputs required by this pinned Blender adapter. Keep the Python execution tool unchecked in the preset.
- Export a self-contained GLB from temporary Blender data. Restore the original file, active scene and selection after success or error, and remove only the temporary data. Use an unpublished staging filename and hand the expected file to Studio after the export succeeds. Check file type, path containment, size and GLB format before the production decoder. Reject malformed geometry arguments and unsupported options before starting Blender work. Use a simple traffic cone built from primitives for the first real test, including its dark base and visible contrast in the default 3D scene.
- First focused Red → Green → Refactor cycle exercises a real stdio fixture subprocess through the production connector. Cover handshake ordering, fragmented UTF-8 input, stderr, paginated discovery, EOF and cancellation with a pending request. Add an opt-in real Blender test that checks the expected GLB and confirms the pre-existing Blender file, scene and selection are preserved. Keep fixtures and harnesses in test targets.

## 3. Generalize discovery and connect the hosted feature

- Persist per-user connection settings beside the existing [`agent settings store`](../../Editor/Sources/AdaEditor/Agent/EditorAgentSettingsStore.swift). Wire the accepted visual proposal into [`EditorSettingsWindow`](../../Editor/Sources/AdaEditor/UI/Editor/EditorSettingsWindow.swift). Provide an editable ordered argument list, Connect and Disconnect, tool selection with input details, and clear status and errors. Default to zero selected tools. Reconnect requires a new connection generation, and edits to executable identity or tool schemas invalidate matching selections and pending calls. Localize all UI and errors in English and Russian.
- Validate input in the local connector with a bounded JSON Schema evaluator for supported schemas. The existing Cloud action validator serves the fixed envelope. Evaluate external schemas separately and reject unsupported assertions or external references during setup. Bind each alias to server identity and schema fingerprint. Bound and sanitize discovery, descriptions and JSON/text results. Keep stderr local, decline reverse requests beyond supported capabilities, and recheck the project, connection, selected tool and schema after approval. Test two real fixture servers with the same tool name and test invalid, disabled, changed and cancelled operations through the production permission path.
- Add the `editor_external` family and patch the [`EditorCloudToolCatalog`](../../Editor/Sources/AdaEditor/Agent/EditorCloudToolCatalog.swift), [`EditorCloudAgentService`](../../Editor/Sources/AdaEditor/Agent/EditorCloudAgentService.swift) and the catalog exporter. Start with grouped v3 as a versioned addition to v2. Preserve `toolContract: 2` for existing Web/mobile and old desktop clients. Add an advertised capability for v3 so new desktop can opt in when it has currently selected local tools. Bind the negotiation per turn and fall back through grouped v2 and legacy where appropriate. `list` and `describe` use cached local discovery in Ask, Plan and Build. `invoke` is Build-only and uses the existing permission card for each call, including the Blender preset. Cloud receives the fixed family and bounded results through the existing model request flow.
- Update the validator pin and add the matching version in `adaengine-service` using [`export-ada-ai-tool-contract.py`](../../Editor/scripts/export-ada-ai-tool-contract.py). Use the existing [`Editor/script/test_cloud_ai.py`](../../Editor/script/test_cloud_ai.py) harness against disposable AIService and Billing instances with appropriate provider fixtures. Verify the backend accepts v3 desktop requests in allowed modes, rejects fabricated Plan invokes and unsupported hosts, preserves v2 and legacy requests, and matches the authored catalog pin. Run `EditorCloudAgentTests`, `EditorLocalizationTests` and the WebUI catalog and agent suites. Keep connection commands, server credentials and local binary artifacts on the desktop.
- The service checkout is absent from this workspace. Its validator change and staged deployment are release dependencies. Land and verify the Ada Cloud contract before enabling shipped clients. The local connector, Blender export/import, and production dispatch tests with an injected hosted transport can proceed independently of service access.
