# Defer render-world work between on-demand window frames

Status: approved.

## Problem

The native SocialFeed benchmark uses the default `WindowGroup` composition and the standard on-demand UI camera. The main world advances on each display tick. The render world still clears its transient entities, runs extraction, and invokes its scheduler even when the window has no presentation request.

In a diagnostic Release build with the full set of default plugins, suspending the render world on ticks without a window request cut median scroll CPU from 867 to 781 ms. Six out of six matched pairs favored the probe, and all AdaUI endpoint images matched. The separate idle series measured 456 versus 342 ms CPU per second. A second series separated extraction from the render scheduler. Its control used 887 ms CPU, the whole-subworld probe used 800 ms, and preserving extraction while skipping the render scheduler used 878 ms. These prototypes establish the cost of the work. They use a fixture with one stable surface and do not represent the production eligibility policy.

A later frame-density sweep used the current engine and the local SAGA buffer-upload improvements. Six interleaved pairs per workload measured a median AdaUI–GPUI CPU gap of 662 ms without input and 780 ms during the standard 60-event scroll, over equal 1.9-second windows. The median of the paired gap ratios was 82%. The 15-, 30-, and 60-event variants traversed the same distance and ended on the same pixels within each app. Separate ScreenCaptureKit runs observed the corresponding number of viewport changes, including zero changes without input. Idle measurements ranged from 513 to 914 ms CPU in AdaUI. This sweep quantifies the no-input gap without attributing it to a specific engine stage. The earlier render-world experiment isolates the portion addressed by the proposed policy.

An idle comparison on the current engine normalized CPU by actual main-world ticks. Four rotated series used the same diagnostic binary across three modes, with six windows of 120 ticks per launch. The full path used 2.80 ms CPU per tick. Preserving extraction and replacing the render schedule with an empty schedule used 2.41 ms. Skipping the render subworld used 1.98 ms, a median paired reduction of 32.2% from the full path. All modes sustained about 120 main-world ticks per second. The scored windows contained no presentation requests, and all 24 viewport snapshots matched. The remaining idle cost includes the work of advancing the main world.

The prototype that also checks active texture cameras retained the benefit on the same current engine and local SAGA. Six interleaved pairs measured a median paired reduction of 23.7% while idle and 10.0% during a matched scroll. Median scroll CPU was 929 ms on the full path, 835 ms with the prototype, and 121 ms on GPUI. All paired AdaUI endpoint captures matched byte for byte, and separate ScreenCaptureKit runs observed 60 viewport changes in both AdaUI modes.

## Design

At the render-world boundary, derive frame demand after the main scheduler has run and after any previous pipelined render-world update reaches its extraction boundary. The renderer owns the decision. Keep simulation, main-world events, normal input handling, and explicit host-driven render updates on their existing paths.

Enable the initial fast path on macOS with SAGA Metal for the built-in on-demand window pipeline. Require the runtime to establish that its render work supports deferred snapshots. Classify built-in work by its extraction and maintenance contract rather than by a list of system names. Use the per-tick path on other backends and for unclassified or custom render systems, graph extensions, and replaced extractors. Changes to the world composition invalidate the eligibility decision before the next skipped tick.

The frame decision includes the following sources of work.

- An active continuous camera, including one sharing a window with an on-demand camera, or a camera targeting a texture. Explicit offscreen rendering and windows with unknown demand use the ordinary path. Evaluate camera activity and targets after simulation so a camera activated or retargeted this tick gets its frame.
- A new window, resize, pending drawable retry, presentation request, or teardown that requires render work. Retain each request through a failed draw acquisition and acknowledge it at the existing acquisition boundary. Release per-frame surface references and service retirement when a window becomes idle or closes.
- UI geometry rebuilds and per-tick extraction inputs, including `UIRedrawRequest` and pending draw contexts set after `.preUpdate`. Consume these before frame-local state is cleared or retain the corresponding payload until it can be consumed. A window presentation bit alone cannot represent these changes.
- Maintenance that consumes non-replayable component events or retires render resources. Keep that work on its current cadence or use the ordinary render path. The component change journal for mesh extraction covers its documented components and supplies its existing full-snapshot fallback. Other event consumers need their own supported contract before their work can be deferred.

While an eligible world is quiescent, omit full transient-world reconstruction and render scheduling. Preserve elapsed shader time and the required per-tick maintenance across skipped ticks. On the next demand, build the current render snapshot before encoding. Deferred work uses full-snapshot semantics or a verified cursor across the actual skipped ticks. If a subsystem requires an intermediate transition, route that transition through its eager path.

An early return inside `RenderSystem` still pays for extraction and the preceding schedules. That experiment removed graph-update samples without a reproducible CPU gain. Retaining all extraction and skipping the render scheduler is another possible boundary. It preserves extraction-side clock and tracker updates, but the measured scroll benefit was about 1%. The design targets a safe boundary before deferred extraction.

The renderer applies the policy internally to supported compositions through the existing public APIs and scene setup. Record the internal-only documentation rationale in the contribution task for independent review.

## Diagnostic validation

The macOS game-loop probe ran with the experimental gate. The on-demand window held the same pixels across six captures while the simulation logged 480 ticks. The mixed window acquired 450 drawables on 450 steady render ticks, and the continuous-camera window acquired 435 on 435. Both showed alternating colors in the captured window. These counts describe acquisition and sampled window content. The production comparison also needs timing for delivered frames.

The current engine and local SAGA passed the window checks again. With the experimental gate, the mixed window acquired 480 drawables on 480 steady render ticks and the continuous-camera window acquired 450 on 450. An active texture camera combined with an idle on-demand UI window exposed a failure in the diagnostic gate that considers window presentation alone. The full path logged 526 offscreen render completion callbacks. The experimental gate logged only the initial completion. Both runs reached 510 logged simulation ticks and their six window captures held the same color. The production check needs a direct offscreen completion assertion because window captures can miss this failure.

A follow-up diagnostic compared three modes in one binary. The window-only condition again logged only the initial offscreen completion. Including active texture cameras in the post-update decision restored 544 completions by the run that logged 540 simulation ticks. The six window captures remained visually stable. The guarded mixed and continuous-camera runs acquired 450 of 450 and 465 of 465 steady drawables respectively. In the pure on-demand case, simulation reached 510 logged ticks without a steady render update. This verifies the texture eligibility condition for a static camera in the fixture.

A transition diagnostic exercised two cases after the main world's pre-update stage. It activated a previously inactive texture camera, and it retargeted an active on-demand camera from a window to a texture. In both cases, window demand was false at transitions on ticks 120 and 240. The full and texture-aware paths prepared the offscreen target on those same ticks and on all 60 ticks of each active interval. GPU completion callbacks confirmed the offscreen work executed. The window-only gate skipped all those frames. The result reproduced with render pipelining enabled when the witness recorded the source tick during extraction and read that snapshot in the render world. Production verification still covers ownership on skipped ticks and transitions that start or resume window presentation.

## Verification

- Cover native regular, on-demand, and mixed camera windows. Verify ongoing game ticks during idle and timely rendering for a camera activated or retargeted in the current tick. Require continuing offscreen completions from an active texture camera in a world with an idle on-demand window.
- Exercise drawable acquisition failure and recovery, window startup, resize, close, and a frame explicitly requested by the host. Check that pending UI geometry and presentation work reaches the correct frame.
- Cover UI invalidations generated after `.preUpdate`, removed-component tracking, shader clock advancement, retirement after the last active camera, and addition of a custom extraction system. Verify that the render world's gate respects pipelined ownership and never reads resources while a prior update is using them.
- Re-run SocialFeed with all default plugins in both Release variants. Use at least six paired scrolls with equal viewport and endpoints. Compare presentation requests with app-attributed presents or timestamped captures of the updated window. In the wake-up test, the first requested update must appear without a second event. Its 95th-percentile latency must stay within one display interval of the control. Record idle render scheduler and extraction calls independently of timing. Report unverified GPU configurations and obtain independent review before landing.
