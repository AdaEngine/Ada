# Local MCP tools in Ada AI

Status **Accepted** · 2026-11-23

Approval was given in the project conversation. See the [implementation plan](../Plans/ada-ai-external-mcp.md).

## Goal and first release

Desktop Studio users can connect a local Model Context Protocol (MCP) server to built-in Ada AI, choose which of its tools the assistant can use, and approve calls in the conversation. The first verified integration is MCP for Blender on Windows and macOS. A user can ask Ada AI in Build mode to make a simple model in Blender, export a self-contained GLB, import it into the current project, put it in an open 3D scene, and check it in visible Play.

The initial connector launches user-configured local executables over standard input and output. This release covers MCP tool discovery and calls with JSON object inputs and bounded text or structured JSON outputs. Studio reports unsupported protocol or tool capabilities during setup. Streamable HTTP, remote authentication, MCP resources, prompts and apps, and Web and mobile execution are candidates for separate designs. ACP, AdaMCP and BYOK keep their current contracts. See [the architecture decision](../ArchitectureDecisions/0032-ada-ai-desktop-external-tools.md).

## Setup and permissions

1. Add a **Local MCP servers** group under **Settings → Agents**. Each entry has a unique display name, executable and ordered arguments. Settings belong to the local Studio user. A project or shared file cannot register commands or opt into tools. Launch uses an argument array, a separate non-project working directory, and the environment needed by the executable and OS. Studio does not copy Ada Cloud credentials or project-specific environment variables into the child process.
2. Studio starts a newly configured executable after an explicit **Connect** action. The setup message explains that the process runs with the user's OS privileges. Studio negotiates MCP, lists tools and shows connections and errors. Tools start unchecked. Users select by name and can review descriptions and input details before enabling them. Changes to connection identity or a selected tool's input contract require review again. Disconnect stops the Studio-owned connection, withholds calls immediately, and leaves the chosen tool settings available for reconnecting to the same configuration.
3. Ada AI can list the enabled tool aliases and read their bounded descriptions and schemas in Ask, Plan, or Build. Ask and Plan use the local catalog already collected at setup and have no MCP call action. Build asks once per call, identifying the project, server, tool, and material arguments or destination. Rejection or Deny permission mode blocks the call. Studio checks the same project, server identity, schema fingerprint, and current tool selection again after the permission response. A reconnect cannot silently approve a different executable or tool schema.

The tool allowlist governs what Ada AI can invoke. The server itself runs with the privileges of the desktop account and can perform side effects when it starts or receives a request. Treat descriptions, responses, progress and errors as untrusted data. Accept only the protocol operations needed for the release and decline server requests for sampling, elicitation, or workspace roots. Keep tool results bounded, render returned text as data, and omit raw stderr, secrets, binary media, and unrelated workspace files from the model context. A server failure or timeout produces a localized explanation in the same chat. Cancellation discards late results and prevents later import or scene edits. If a server may have already acted, report the outcome as uncertain and await a deliberate retry.

Use existing Studio settings groups, labeled inputs, buttons and chat permission cards. Show separate connecting, connected and error states with an actionable message. Use real buttons for Connect and Disconnect, and checkboxes for tool selection. Keep keyboard focus and long executable paths readable at narrow widths. The visual proposal covers connection and selection. Verify the rendered control and permission card on Windows and macOS with English and Russian text before release.

## Ada AI contract and ownership

- A desktop-owned service manages the MCP subprocess, initialization, paginated tool discovery, bounded results, call deadlines, cancellation and shutdown. Reuse AdaMCP's `Client` for supported protocol behavior and add or adapt a subprocess transport based on the package's actual capabilities on both desktop platforms. Test protocol negotiation, including the version used by the pinned Blender server. Server crashes, disable, project changes and shutdown invalidate affected pending calls.
- Register a fixed grouped tool family, `editor_external`, with `list`, `describe` and `invoke`. `list` returns selected tool aliases and short summaries, `describe` returns the chosen tool's bounded schema, and `invoke` takes the alias and a JSON arguments object. The local service resolves the alias, checks the exact selected tool and validates input against its advertised schema before permission or execution. Reject external schema references and show a setup error for other schemas Studio cannot validate. Tool identity includes the local server and schema fingerprint so duplicate tool names on different servers remain distinct. Reserve a single model-facing family for the feature and bound list and schema sizes. Server text never changes the cloud function definitions.
- Extend the hosted grouped catalog additively and publish the matching Ada Cloud validator pin before enabling the client feature. Keep the 17 existing families and allow one additional desktop family in the new contract. Pin the negotiated contract per turn and support the existing grouped and legacy contracts on older Cloud deployments. Advertise the new family only to eligible desktop turns with configured tools. On compatible servers, the Cloud validates the known envelope and Ask/Plan policy before model submission. Studio owns discovered schemas, credentials, permissions, and actual tool calls. A compatible server and an enabled local tool are both needed to expose an action. See [the existing catalog design](ada-ai-tool-consolidation.md).

The fixed Cloud envelope keeps validation and billing inside the existing Ada AI turn loop and lets users register new local servers without a Cloud release for each server. A direct Blender CLI integration would cover model creation alone. Sending every discovered tool schema as a cloud function would change Cloud's schema trust boundary and consume a function slot per tool.

## Blender workflow

Use the separately installed MCP for Blender server and add-on. The setup guide shows how to use a tested server version and connect to Blender on loopback. Studio offers a Blender preset that uses the same MCP connector and checks the expected tool name and schema. The preset exposes a typed `create_and_export_glb` action for simple, static props made from primitives with transforms and material colors. Its local adapter supplies a Studio-owned Blender script and passes the recipe as validated data. The script and export path are both Studio-owned. The generic connector honors tools that the user explicitly enables, including any general-purpose scripting tool they choose to trust.

| Step | Behavior and evidence |
| --- | --- |
| Create and export | Show the model name and target project before approval. Create the prop in an isolated temporary Blender scene and export only that scene as glTF 2.0 binary, with embedded resources and without compression extensions. Preserve the user's open Blender document and selection. Studio allocates a job path under project-local `Downloads`, constrains where the exporter can write, and verifies that the expected file is a regular, self-contained GLB within the importer budget. Job results expose a project-relative artifact reference. |
| Import | Run the existing model importer with that artifact and the declared project Assets root. The importer validates before copying, preserves existing files, and returns the exact portable `@res://` reference. Associate the receipt with the job so a retry after import reuses that asset. If the outcome is uncertain, reconcile the expected artifact against the project's import state before another write. |
| Place | Place a `Model3DSource` in the requested, open scene using its current revision and normal undo and save path. Use the expected reference and sensible scale. Ask the user to choose the destination if it is ambiguous. Keep the completed asset if placement is declined or the scene changed. A retry reads the latest scene and checks for the existing placement before applying another edit. |
| Verify | Start visible Play for that scene. Require the current run to contain the exact imported reference and a live instantiated model root with no load error. Capture a fresh completed game-camera frame attributable to that run. A blank frame or stale run is insufficient for visual confirmation. Keep Play visible and provide the local PNG path for the user or QA to inspect. The current text-only provider reports runtime evidence and capture status. Visual confirmation comes from inspecting the viewport or PNG. |

Bind the job to its project, destination and scene identity. Use isolated job directories and clean up only Studio-owned staging data after import or failure. Preserve completed assets and authored edits on later failure. Reject missing or malformed exports, external references, escaping paths and partial files before import. Reject stale scene revisions or a mismatched running game before continuing. Return the last completed stage and the next action available to the user. Keep project and tool activity on the existing Studio surfaces.

Exercise the production connector and Cloud turn loop. Verify old grouped and legacy Cloud compatibility and the new server validator against real request fixtures.
